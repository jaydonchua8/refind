# refind

Replay a recorded browser-use 1.0 run without a model, and stop instead of clicking the wrong thing.

This is an independent prototype. It is not affiliated with, reviewed by, or endorsed by Browser Use. All benchmark data is synthetic and generated by `sim.py`. The replay hook has only been run against a simulator in this repository, never against the real library or a real browser.

## The problem

In browser-use 1.0 the model drives the page by writing Python cells. In ultrafast mode it reads the page as a text listing and acts on Chrome `backendNodeId`s:

```
[state] Team | Northwind Admin | https://admin.example.test/team
## Team members
[227] textbox "Search members"
elena@example.test Admin
[231] button "Edit"
[236] button "Remove"
[/state]
```

```python
bu.click(236)   # prints: [ok] click [236] button "Remove" -> page changed
```

A finished run leaves a transcript of those cells and their output. Repeating the task should not need the model again, but the ids in the transcript are only valid for one page load. On the next visit `236` is a different node or no node. And the page itself drifts between runs: rows are added and reordered, a cookie banner appears, a button is relabelled, the thing the run acted on is gone.

So replay needs two things: a way to say "the Remove button in elena's row" without the id, and a rule for when to give up. Clicking another user's Remove button is much worse than stopping and asking the model.

## Why this matters to Browser Use specifically

Things I checked in the public repository (github.com/browser-use/browser-use, version 1.0.8, commit 753d629) and on their pages:

- 1.0 removed replay. `MIGRATING.md` lists `save_history()`, `load_and_rerun()`, `rerun_history()`, `AgentHistoryList.save_to_file()` and `load_from_file()` as removed, with the replacement "`result.messages` holds the transcript; run the task again". `browser_use/legacy.py` and `browser_use/agent/views.py` raise a "removed" error for each of them.
- The DOM serializer and element indexes that 0.x replay depended on are gone as well. `legacy.py` answers any `browser_use.dom` import with "there is no DOM, Page or Element API".
- What exists instead is `browser_use/ax.py`. `AxHelpers.state()` prints the listing above from `Accessibility.getFullAXTree`, and the prompt in that file says "Ids are Chrome backendNodeIds". The default system prompt in `browser_use/agent/prompt.py` says "IDs expire after navigation".
- The intern listing text I was working from names "rerun agent workflows deterministic" as one of four open problems. (The YC jobs page I could load on 2026-11-23 showed the listing title, location and pay, not the description.)

The first version of this project fingerprinted HTML elements with attributes, classes and XPaths, and said the hook would be the 0.x action history. That interface no longer exists, so I rewrote the project around what 1.0 actually exposes: the printed listing, the `[ok]` action lines, and the transcript.

## What it does

1. `axstate.py` parses the `[state] ... [/state]` listing and the `[ok] click [id] ...` lines back into structured data. The rules (name printed raw and clipped at 150 characters, value JSON-quoted and clipped at 100, the fixed order of state words, the two spaces before `options:`) were read from `ax.py`.
2. `transcript.py` reads a run's messages in the JSON shape that `browser_use/agent/loop.py` `_plain()` writes (`kind`, `parts`, `part_kind`, `tool_name`, `args`, `content`), pairs every `bu.click(id)` and `bu.type(id, text)` in the code with the `[ok]` line it printed, looks the id up in the last listing the model had seen, and replaces it with a fingerprint.
3. `refind.py` holds `fingerprint(state, id)` and `find(fingerprint, state)`. A fingerprint has no id in it. `find` returns the new id or a reason for refusing.
4. `replay.py` runs the plan against any object with `state()`, `click(id)` and `type(id, text, enter=False)`, which are the signatures of `AxHelpers`. It checks the page address and toggle states before each action and the outcome line after it, and returns a handoff when anything differs.

## Architecture

```
transcript JSON --> transcript.compile_plan --> plan: goto / click / type / opaque steps
                        (uses axstate.split_output and refind.fingerprint)
plan + bu --> replay.replay --> completed | handoff {step, reason, acted}
                        (per step: bu.state() -> axstate.parse_state -> refind.find -> bu.click / bu.type)
sim.py   synthetic sites, drift operations, FakeBu (stands in for AxHelpers), recorder
bench.py element-level and task-level benchmark, train and held-out splits, tuning
```

| file | lines | role |
|---|---|---|
| `axstate.py` | 272 | listing and action-line parser and writer |
| `refind.py` | 427 | fingerprint, scoring, decision rules, CLI |
| `transcript.py` | 229 | transcript to replay plan |
| `replay.py` | 116 | verified replay and handoff text |
| `sim.py` | 661 | synthetic sites, drift, stand-in for `bu` |
| `bench.py` | 258 | benchmark and tuning |
| `demo.py` | 79 | walk-through |
| `test_refind.py` | 561 | 46 tests |

## Key decisions and tradeoffs

**Repeated controls are identified by their row, not their position.** When a role and name repeat (Edit, Edit, Edit), the fingerprint keeps the lines of that element's row and weighs each token by how few of the other rows also contain it. The row's own label weighs 1, the word "button" weighs 0. The row is found by walking from the element towards the previous twin and stopping at the farthest line that is not itself a repeated control. If the label is no longer next to any candidate, the answer is a refusal, because the likeliest explanation is that the row was removed. A row never takes more labelled lines than it had when recorded, so a neighbouring item that lost its own button (out of stock, say) is not read as part of the next row.

**Row labels are assumed to come before the controls, with one check.** That is how the listing prints a table row or a card. If nothing stands in front of the first twin while text follows the last one, the fingerprint switches to label-after. A list that mixes both, or a grid where the listing interleaves two rows, will get this wrong.

**A relabel is only accepted with evidence.** A candidate with a different name is accepted only if it shares words with the old name, sits in the same surroundings, and its name was not already on the recorded page as some other element (the fingerprint stores a hash of every role and name on the page for this). "Sign in" to "Log in" passes. "Remove" to "Delete" is refused, because from the listing alone it cannot be told apart from a new feature that replaced the old one. This costs completions and I think it is the right default.

**An exact unique name beats a look-alike in the old position**, so "Sun Hat" is not confused with a new "Sun Hat Kids" row inserted where it used to be. If the only exact match now sits under a different heading without its surroundings, it is refused.

**Only cells I fully understand are replayed.** A cell must be straight-line calls to `new_tab`, `goto_url`, `wait_for_load`, `bu.state`, `bu.click`, `bu.type` with literal arguments, and the `[ok]` lines must match the code one for one. Loops, `js()`, raw `cdp()`, a recorded action that failed, an id that is not in the last listing, an id used after a navigation, and redacted `<secret:name>` text all become an "opaque" step where the replay stops. The cost is that real transcripts with data extraction in the middle will hand off early.

**Postconditions are part of the plan.** Each step stores the recorded outcome (`navigated to <url>`, `page changed`, `no change`). If the replayed action prints something else, the replay stops and the handoff says the action was already sent.

**Thresholds were tuned on synthetic data, with a split.** Weights and thresholds come from a random search on two synthetic sites where a wrong match costs 25 refusals. Two other sites with a different drift mix and other seeds are held out. Two small rules were added by hand after reading train failures; the comment above `PARAMS` in `refind.py` says which. The row-size cap described above was added after I listed the wrong matches of both splits, so the held-out numbers below are not untouched by that one change: before it, held-out had 4 wrong matches on removed elements and 2 wrong-click replays; after it, 2 and 1.

## Install and usage

Python 3.9 or newer, standard library only. Nothing to install.

```
python demo.py                     # one-minute walk-through
python -m unittest test_refind     # 46 tests, a few seconds
python bench.py --quick            # small benchmark
python bench.py                    # full benchmark, a few minutes, rewrites bench_results.json
python refind.py compile sample_transcript.json
python refind.py find fingerprint.json state.txt
```

In code:

```python
import json
from transcript import compile_plan
from replay import replay, handoff_prompt

plan = compile_plan(json.load(open("sample_transcript.json")))
result = replay(plan, bu, goto=goto_url)     # bu: state(), click(id), type(id, text, enter=False)
if result["status"] == "handoff":
    print(handoff_prompt(plan, result))      # text to continue the task with a model
```

`sample_transcript.json` is a synthetic transcript written by `sim.py`.

## Tests and verified results

`python -W error -m unittest test_refind` runs 46 tests and passes. They cover the parser (including the expected output string from browser-use's own `tests/ci/test_ultrafast.py`, a 3000-line fuzzed round trip, cut and incomplete listings), the matcher (moved rows, removed rows, a row that lost its button, look-alikes, relabels, copies elsewhere, label-after lists, frames), the compiler (ten kinds of cell that must not be replayed), the replay (every handoff reason, including page text forged to look like a control), the simulator, and the CLI.

Benchmark, `python bench.py`, 20 seeds per split, SYNTHETIC sites. Each page gets 1 to 3 of 13 drift operations (banner, reorder, insert rows, remove row, drop control, relabel, button/link swap, number changes, heading change, extra controls, a copy elsewhere, toggled checkbox, feature replaced).

Element level. "Still there" means the element exists after the drift; "removed" means it does not, so the only right answer is to refuse.

| split | method | still there | found | wrong | refused | removed | refused | wrong |
|---|---|---|---|---|---|---|---|---|
| train | role+name, nth match | 9608 | 80.6% | 12.5% | 6.9% | 544 | 72.2% | 27.8% |
| train | role+name, only if unique | 9608 | 55.1% | 0.0% | 44.9% | 544 | 88.8% | 11.2% |
| train | refind | 9608 | 97.8% | 0.01% (1) | 2.2% | 544 | 99.4% | 0.6% (3) |
| held out | role+name, nth match | 7153 | 81.4% | 10.7% | 7.8% | 491 | 72.3% | 27.7% |
| held out | role+name, only if unique | 7153 | 51.9% | 0.0% | 48.1% | 491 | 87.6% | 12.4% |
| held out | refind | 7153 | 95.1% | 0 of 7153 | 4.9% | 491 | 99.6% | 0.4% (2) |

Replaying the recorded id itself finds 0.0% in both splits, as expected.

Task level. A scripted multi-page run (5 to 9 actions) is recorded, compiled from its transcript, and replayed on a site where every page drifted. 240 replays per split. "Wrong click" means at least one action reached an element other than the recorded one.

| split | method | completed correctly | stopped, all actions so far correct | wrong click | actions done without a model |
|---|---|---|---|---|---|
| train | role+name, nth match | 18.8% | 51.7% | 29.6% | 38.3% |
| train | refind | 54.6% | 45.0% | 0.4% (1) | 72.7% |
| held out | role+name, nth match | 14.6% | 54.2% | 31.2% | 31.5% |
| held out | refind | 36.2% | 63.3% | 0.4% (1) | 57.7% |

Of the held-out replays, 132 could have been completed as recorded on the drifted site (no target removed, no toggle already flipped). refind completed 87 of those, 65.9%. On train it was 131 of 156, 84.0%. Most of the gap is relabels with no shared words, which refind refuses on purpose (the held-out stop reasons were 66 `renamed_unsure`, 64 `not_found`, 21 `state_differs`, 1 `context_lost`). Neither of the two wrong-click replays (one per split) went on to complete; both ended in a handoff.

Exact counts are in `bench_results.json`.

## Limitations and next steps

- Not run against browser-use, browser-harness or Chrome. `FakeBu` in `sim.py` imitates the text format and signatures of `AxHelpers` as I read them. The only real browser-use output in the repository is one expected string copied from their test file. The first next step is to run `replay` with the real `bu` on recorded runs and see how the listing behaves on real sites.
- The transcript shape is the one `_plain()` writes. I assume a plain Pydantic AI dump of `result.messages` uses the same `part_kind`, `tool_name`, `args` and `content` keys but did not verify that against the pinned Pydantic AI version.
- Ultrafast mode only. In default mode the model filters the accessibility tree itself and prints whatever it likes, so there is no listing to fingerprint.
- All numbers are from synthetic sites that I wrote, with drift operations that I chose. The held-out split guards against tuning to the exact sites, not against my idea of how sites change being wrong.
- The 6 wrong matches at element level: three are a removed item whose near-namesake stayed ("Day Pack" removed, "Day Pack Kids" present), two are a removed button with a copy of it elsewhere on the page whose surroundings scored just over the bar, and one is a cart row matched to a row with an almost identical label.
- The printed listing is ambiguous in two places: a name that contains `" = "`, and page text that looks exactly like a control line. The second cannot make the replay click a different real element, because the forged id does not exist and the click fails, but it can cause an unnecessary handoff.
- Listings cut by `bu.state(max=...)` are refused outright. A real integration should ask for the full listing.
- Chained actions in one cell are fingerprinted from the listing before the cell, since that is all the transcript has.
- Opaque cells with no ids can be passed to a `run_cell` callback, but variables from earlier cells will not exist if those were replayed through `bu`. A better design would emit a Python script for the same REPL, with ids replaced by lookups.
- No shadow-root or cross-origin iframe handling beyond what the listing prints as `--- frame url ---`.
